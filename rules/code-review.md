# PR 리뷰 규칙

이 리포의 PR 을 리뷰하는 에이전트(Claude / Codex)와 사람이 함께 쓰는 기준.
목표는 "그럴듯한 코멘트"가 아니라 **근거 있는 리뷰**다 — 실제 코드 경로를 읽고, 가능하면 CI 결과로 뒷받침한다.

## 리뷰 SLA

- **PR 리뷰는 요청받은 뒤 이틀(2일) 이내에 처리한다.** 블로킹이 없으면 approve, 있으면 근거와 함께 남긴다.

## 리뷰 태도

- **추측 금지.** 코드를 실제로 읽고 말한다. 파일·라인을 지목한다 (`src/scoreCake.js:42` 형식).
- 근거 우선 → 근거가 선 뒤 **하나의** 가설을 제시한다. 여러 추정을 나열하지 않는다.
- 스코프를 존중한다. PR 이 다루지 않은 파일의 개선은 "참고"로만, 블로킹하지 않는다.
- 칭찬도 구체적으로. 무엇이 왜 좋은지 짚으면 다음에도 반복된다.

## 반드시 확인 (블로킹 사유)

1. **채점 무결성** — `scoreCake.js`/`orders.js` 변경 시: `hidden.wants` 가 프론트로 노출되지 않는가?
   don't-care(주문에 없던 필드)와 "없음(필요없음)"이 뒤섞이지 않는가?
2. **키 노출** — API 키·토큰이 프론트 번들이나 커밋에 들어가지 않는가? 키는 `api/` 서버리스에서만.
3. **빌드** — `npm run build` 가 통과하는가? (CI 가 자동 확인 — red 면 블로킹)
4. **프롬프트 회귀** — `_monsterPrompt.js` 변경 시 `scripts/testChat.py` 로 손님 행동이
   깨지지 않았음을 확인했는가? (정답 유출·힌트 남발 등)
5. **상태머신** — `App.jsx` 흐름(TITLE→PLAYING→RESULT→END)과 케이크 상태 전이가 깨지지 않는가?

## 체크리스트 (권장)

- [ ] JS 유지 (TS 주석 없음), 주변 스타일과 일관
- [ ] 하드코딩된 모델명·경로·키 없음
- [ ] 스코프 밖 파일 변경 없음 (있다면 PR 본문에 이유 명시)
- [ ] 조사(한글 이/가·은/는) 등 사용자 노출 텍스트 자연스러움
- [ ] 새 재료/주문 추가 시 `sheetType()`·`describeCake()`·채점 경로 모두 반영
- [ ] README(사람)·AGENTS(AI) 경계 유지 — 서로 참조하지 않음

## 리뷰 출력 형식

```
### 요약
<한두 줄: 이 PR 이 무엇을 하며 머지 가능한가>

### 블로킹 (있으면)
- [파일:라인] 문제 — 왜 문제인지 + 재현/근거

### 제안 (선택)
- [파일:라인] 개선 아이디어 (블로킹 아님)

### 좋은 점
- 구체적으로
```
